# 예외 처리와 장애 기록

작성: 2026-10-21(3단계 완료 시점). 단계가 진행될 때마다 갱신합니다.

이 문서는 두 부분입니다.

1. **예외 처리 목록:** 코드가 어떤 비정상 상황을 어떻게 다루는지, 계층별로 정리했습니다.
2. **실제로 겪은 장애와 해결:** 개발 중 실제로 부딪힌 문제와 원인·해결·배운 점입니다. 면접의 "어려웠던 점" 질문에 그대로 쓸 수 있습니다.

## 처리 원칙

| 원칙 | 뜻 | 예 |
|---|---|---|
| 버리지 않고 기록한다 | 형식이 틀린 레코드나 이벤트를 조용히 버리지 않고 사유와 함께 남긴다 | `silver.quality_issues`, `silver.stream_rejections` |
| 추측하지 않는다 | 모르는 값을 0이나 비슷한 이름으로 채우지 않는다 | 결측 점수는 `NULL`, 팀 이름은 검토한 대조표로만 연결 |
| 덮어쓰지 않는다 | 소스끼리 다르거나 값이 바뀌어도 이전 값을 지우지 않는다 | 버전 테이블, 불일치는 `SCORE_MISMATCH`로 기록 |
| 한 묶음은 전부 아니면 전무 | 중간에 실패하면 묶음 전체를 되돌린다 | 수집 한 번 = 트랜잭션 하나, 소비자 묶음 = 트랜잭션 하나 |
| 일시적 오류는 다시 시도, 영구적 오류는 바로 실패 | 기다리면 풀리는 오류만 재시도한다 | 429는 재시도, 403은 바로 실패 |
| 실패도 기록한다 | 실행이 실패하면 사유를 남기고, 상시 서비스는 멈추지 않는다 | `ingest.runs.status = FAILED`, 수집기는 5분 뒤 재시도 |

## 1. 수집 입력 검사

### openfootball JSON (`pipelines/ingest/openfootball.py`)

검사를 통과하지 못한 레코드는 Silver에 넣지 않고 `silver.quality_issues`에 원본과 함께 남깁니다. 같은 원본 파일에 대해서는 한 번만 기록합니다.

| 코드 | 상황 | 처리 |
|---|---|---|
| `MISSING_MATCHES_ARRAY` | 파일에 경기 목록이 없음 | 파일 전체를 문제로 기록 |
| `INVALID_RECORD` | 경기 항목이 객체가 아님 | 그 레코드 제외 |
| `MISSING_TEAM` | 홈·원정 팀 이름이 없거나 빈 문자열 | 제외 |
| `SAME_TEAM` | 홈과 원정이 같은 팀 | 제외 |
| `INVALID_DATE` / `INVALID_TIME` | 날짜·시각 형식이 틀림 | 제외 |
| `NONEXISTENT_LOCAL_TIME` | 서머타임 전환으로 존재하지 않는 현지 시각(예: 3월 마지막 일요일 01:30) | 제외. 시간대 라이브러리가 조용히 바꿔 주는 값을 믿지 않고, 되돌려 변환해 확인 |
| `INVALID_SCORE_FORMAT` | 점수가 객체·배열 형식이 아니거나 음수·불리언 | 제외. `True`가 1로 통과하지 않게 따로 막음 |
| `HALF_TIME_WITHOUT_FULL_TIME` | 전반 점수만 있고 최종 점수가 없음 | 제외 |
| `HALF_TIME_EXCEEDS_FULL_TIME` | 전반 점수가 최종 점수보다 큼 | 제외 |
| `DUPLICATE_FIXTURE` | 한 시즌에 같은 홈·원정 조합이 두 번 | 두 번째부터 제외 |

검사 대상이 아닌 "정상적인 결측"은 오류가 아닙니다. 전반 점수가 없는 경기(2025-26 EPL 380경기 중 27경기)는 전반 점수를 `NULL`로 둔 채 저장합니다.

### football-data.co.uk CSV (`pipelines/ingest/football_data_co_uk.py`)

| 코드 | 상황 | 처리 |
|---|---|---|
| 파일 이름 오류 | `E0_2025-26.csv` 형식이 아니거나 시즌 연도가 이어지지 않음 | 파일을 읽지 않음(ValueError) |
| `MISSING_COLUMNS` | 필수 열(Div, Date, HomeTeam, AwayTeam)이 없음 | 파일 전체를 문제로 기록 |
| `UNEXPECTED_DIVISION` | 리그 코드가 파일 이름과 다름 | 그 행 제외 |
| `INVALID_TEAMS` | 팀 이름이 없거나 같음 | 제외 |
| `INVALID_VALUE` | 날짜·점수·시각 형식 오류(옛 dd/mm/yy 형식은 정상으로 처리) | 제외 |
| `PARTIAL_SCORE` | 홈·원정 점수 중 하나만 있음 | 제외 |
| `DUPLICATE_FIXTURE` | 같은 대진이 두 번 | 두 번째부터 제외 |
| `INVALID_PRICE` | 배당이 숫자가 아니거나 1 이하(실제 사례: 2021-22 뉴캐슬-맨시티 언더오버 배당 "0") | 그 배당만 저장하지 않고, 같은 행의 다른 배당은 저장 |
| `INVALID_HANDICAP_LINE` | 핸디캡 기준선이 숫자가 아님 | 그 시점의 핸디캡 배당만 제외 |
| `UNMAPPED_TEAM` | 팀 이름이 검토한 대조표에 없음 | 제외. 이름이 비슷해도 추측하지 않음 |
| `MATCH_NOT_FOUND` | 대조는 됐지만 openfootball에 그 경기가 없음 | 제외 |
| `DATE_MISMATCH` | 두 소스의 경기 날짜가 다름 | **연결은 유지**하고 기록만. 어느 쪽이 맞는지 판단하지 않음 |
| `SCORE_MISMATCH` | 두 소스의 최종 점수가 다름 | 연결은 유지하고 기록만. openfootball 값을 덮어쓰지 않음 |

시즌마다 열 구성이 달라(106~132개) 열 위치가 아니라 열 이름으로 배당을 찾습니다. 옛 파일의 `BFD`(Betfair 무승부 열)와 새 파일의 `BFD`(북메이커 코드)가 겹치는 경우도 구분합니다.

## 2. 외부 API (`pipelines/ingest/football_data_org.py`)

| 상황 | 처리 | 이유 |
|---|---|---|
| 분당 10회 한도에 가까움 | `RateLimiter`가 최근 60초 요청 수를 세어 한도면 기다림 | 막히기 전에 스스로 늦춤 |
| 서버가 남은 횟수 0이라고 알려 줌 | 응답 헤더의 초기화 시간까지 멈춤 | 같은 키를 다른 곳에서 써도 서버 기준을 따름 |
| 429 Too Many Requests | 헤더의 초기화 시간(없으면 60초)만큼 기다렸다 최대 3번 시도 | 일시적 오류라 기다리면 풀림 |
| 403·404 등 다른 HTTP 오류 | 재시도하지 않고 바로 실패 | 키 문제·주소 문제는 기다려도 안 풀림 |
| API 키 없음 | 시작하자마자 명확한 메시지로 실패 | 키 없이 요청해 한도를 낭비하지 않게 |
| 조회 중 아무 예외 | `ingest.runs`에 FAILED와 사유 기록, 수집기는 5분 뒤 다시 시도 | 상시 서비스가 네트워크 오류 하나로 멈추지 않게 |
| 응답이 지난번과 같음 | 이벤트를 보내지 않음 | 할 일이 없는 것은 오류가 아님 |
| openfootball 시즌 파일이 아직 없음(404) | Airflow 태스크를 실패가 아닌 "건너뜀"으로 | 새 시즌이 올라오기 전은 정상 상황 |

## 3. 스트리밍 (`pipelines/streaming/`)

### 경기 이벤트 소비자 (`match_consumer.py`)

| 결과·코드 | 상황 | 처리 |
|---|---|---|
| `INVALID_JSON` | 메시지가 JSON이 아니거나 UTF-8이 아님 | `silver.stream_rejections`에 원본 앞부분과 함께 기록, 다음 메시지로 |
| `MISSING_FIELDS` | 이벤트 겉봉투 필수 필드 누락 | 기록 후 다음으로 |
| `UNSUPPORTED_SCHEMA_VERSION` | 모르는 형식 버전 | 기록 후 다음으로. 조용히 잘못 해석하지 않음 |
| `MISSING_PAYLOAD_FIELD` | 내용에 리그·시즌·팀·경기 ID가 없음 | 기록 후 다음으로 |
| `UNMAPPED_TEAM` | 팀 ID가 대조표에 없음 | 기록 후 다음으로 |
| `STALE_EVENT` | 출처의 갱신 시각이 이미 저장된 최신 버전보다 이름(늦게 도착한 옛 정보) | 저장하지 않고 기록. 최신 값을 덮지 않음 |
| `DUPLICATE` | 직전 버전과 내용이 같거나, 이미 반영한 event_id | 아무것도 하지 않음(정상이라 기록도 안 함) |
| 묶음 처리 중 DB 오류 | 묶음 전체 롤백, 오프셋 커밋 안 함 | 다시 시작하면 같은 묶음부터. 반쯤 저장된 상태가 없음 |
| Kafka 메시지 오류 | 예외를 올려 묶음 롤백 | 위와 같음 |
| 같은 메시지 재처리 | 거부 기록은 `UNIQUE(topic, partition, offset, reason)`로 한 번만 | 재처리해도 기록이 불어나지 않음 |


| 단계 | 코드·상황 | 처리 |
|---|---|---|
| 보내기 전 | 지원하지 않는 시장, 선택지 누락, 배당이 숫자 아님·1 이하·1000 초과, 언더오버 기준점 없음, 시간대 없는 시각, 팀 미입력 | 한 줄 오류 메시지와 종료 코드 2. 아무것도 보내지 않음 |
| 소비자 | `INVALID_EVENT` | 이벤트를 해석할 수 없음 → 거부 기록 |
| | `MATCH_NOT_FOUND` | 리그·시즌·팀으로 경기를 못 찾음 → 거부 |
| | `POST_KICKOFF` | 배당을 본 시각이 경기 시작 이후 → 거부(경기 전 입력이 될 수 없음) |
| | `STALE_EVENT` | 이미 저장된 값보다 이른 시각에 본 배당 → 거부 |
| | `DUPLICATE` | 모든 선택지 값이 같음 → 저장 안 함 |
| 보낸 뒤 | `PENDING` | 30초 안에 처리 결과가 없음 → 소비자가 꺼져 있을 수 있다고 안내 |

## 4. 저장소·인프라

| 대상 | 상황 | 처리 | 위치 |
|---|---|---|---|
| 설정 | `.env`가 없거나 비밀번호가 빠짐 | 어떤 값이 없는지와 `init-env` 실행 안내 | `pipelines/config.py` |
| 설정 | `.env`가 이미 있는데 다시 만들려 함 | 덮어쓰지 않음(DB 볼륨 비밀번호와 어긋나지 않게) | `init_env` |
| Postgres 연결 | 컨테이너가 꺼져 있음 | 10초 안에 실패(`connect_timeout=10`) | `Settings.postgres_conninfo` |
| 스키마 이전 | 여러 프로세스가 동시에 migrate | advisory lock으로 한 번만 적용, 파일 하나 = 트랜잭션 하나 | `pipelines/db.py` |
| 동시 수집 | 같은 데이터셋을 두 프로세스가 동시에 수집 | 데이터셋 단위 advisory lock으로 버전 번호가 겹치지 않게 | 각 수집기 |
| S3 버킷 | 버킷이 없음 | 만든다 | `object_store.ensure_bucket` |
| S3 객체 | 없는 객체 조회 | 404만 "없음"으로, 그 밖의 오류는 그대로 올림 | `object_exists` |
| Bronze 저장 후 DB 실패 | 내용 해시 경로라 다음 실행이 같은 객체를 그대로 다시 씀 | 수집기들 |
| Kafka 토픽 | 이미 있는 토픽 생성 | `TOPIC_ALREADY_EXISTS`만 무시 | `kafka_io.ensure_topics` |
| Kafka 토픽 | 없는 토픽 삭제 | `UNKNOWN_TOPIC`만 무시, 삭제 완료까지 기다림 | `kafka_io.delete_topics` |
| Kafka 생산자 | 전송 실패 | 전달 결과 콜백으로 확인해 예외, `flush` 후 남은 메시지가 있으면 예외 | `publish`, `flush` |
| 컨테이너 | 서비스가 아직 준비 안 됨 | 상태 검사(healthcheck)가 통과해야 다음 서비스 시작 | `infra/docker-compose.yml` |
| 컨테이너 | 프로세스가 죽음 | `restart: unless-stopped`로 다시 띄움 | 같은 파일 |
| Airflow | 태스크 일시 실패 | 2회 재시도, 간격 지수 증가 | DAG `default_args` |
| Airflow | 일부 시즌 건너뜀 | dbt는 "실패가 없으면" 실행(`none_failed`) | `openfootball_epl_daily` |
| Airflow | 같은 DAG가 겹쳐 실행 | `max_active_runs=1` | 두 DAG |
| dbt | Windows 기본 인코딩(CP949)으로 한글 파일을 못 읽음 | dbt 실행 시 `PYTHONUTF8=1` | `pipelines/dbt_runner.py` |
| dbt | 품질 테스트 실패 | 종료 코드가 0이 아니어서 Airflow 실행이 실패로 표시 | `run_dbt` |

## 5. DB 제약 (마지막 방어선)

코드에 실수가 있어도 잘못된 데이터가 들어가지 않게 DB가 거부합니다.

| 종류 | 예 | 막는 것 |
|---|---|---|
| 수정·삭제 차단 트리거 | `raw_files`, `fetches`, `team_aliases`, `match_revisions`, `quality_issues`, `odds_revisions`, `live_match_revisions`, `stream_rejections`, `prematch_inputs`, `backtest_runs`, `backtest_predictions`, `evaluation_reports`, `prematch_predictions`, `prospective_reports` | 이력 덮어쓰기(평가 기준을 나중에 바꿔 "통과"로 고쳐 쓰는 것 포함) |
| CHECK | 점수 0 이상, 홈·원정 점수는 둘 다 있거나 둘 다 없음, 전반만 있고 최종이 없는 경우 금지, 배당 > 1, 허용된 시장·선택지·시점·상태만 | 형식이 틀린 값 |
| CHECK | 스냅샷이 TAKEN이면 입력·기준 시각·해시가 반드시 있음 | 반쯤 저장된 스냅샷 |
| CHECK | 홈 팀 ≠ 원정 팀 | 잘못된 경기 |
| 외래 키 + CHECK | 경기 전 예측의 기준 시각 = 스냅샷 기준 시각, 기록 시각은 그 뒤 10분 안, 학습 경기는 기준 시각 이전, 검증되지 않은 모델은 READY 불가 | 나중에 만든 예측·새 모델 소급, 검증 전 확률 표시 |
| CHECK | 백테스트 예측: 학습에 쓴 마지막 경기 + 3시간 ≤ 학습 기준 시각 ≤ 경기 시작, 확률 셋 모두 양수·합 = 1, PREDICTED면 확률 있음·WITHHELD면 사유 있음 | 누수된 예측, 확률이 아닌 값 |
| UNIQUE | 같은 리그·시즌·홈·원정 경기는 하나, 같은 원본(해시)은 하나, 경기·시점당 스냅샷 하나, 모델 버전 × 목적 × 평가 시즌 × 데이터셋 해시당 백테스트 실행 하나 | 중복 |

## 6. 시점·누수 관련 방어

| 장치 | 내용 |
|---|---|
| 기준 시각 함수 `*_known_at(as_of)` | 발표 시각과 받은 시각이 모두 as_of 이하인 버전만 고름 |
| 늦은 도착 거부 | 출처 갱신 시각이 더 이른 정보는 최신 값을 덮지 못함(`STALE_EVENT`) |
| 놓친 스냅샷을 채우지 않음 | 90분 유예를 넘기면 MISSED. 최근 7일 안 경기는 PC가 꺼져 있었어도 MISSED로 기록 |
| 학습 데이터셋 누수 검사 | dbt 테스트 + Python 독립 재계산(2,280행 불일치 0) |
| 마감 배당은 입력으로 쓰지 않음 | 경기 직전 정보를 담고 있어 비교 기준으로만 사용 |
| 백테스트 주 단위 재학습 | 그 주 첫 경기 시작 시각에 결과가 알려진 경기(시작 + 3시간 ≤ 기준 시각)로만 학습. 같은 주 뒤쪽 경기도 같은 기준(`pipelines/modeling/backtest.py`) |
| 검증·시험 시즌 분리 | 하이퍼파라미터는 검증 시즌(2022-23)에서만 고르고, 시험 시즌은 고른 설정으로 한 번만 평가 |
| 근거 부족 시 보류 | 학습 경기 100개 미만이면 확률 없이 `INSUFFICIENT_TRAINING_DATA(<100)`로 WITHHELD |
| 시장 비교는 같은 경기끼리 | 시장 배당이 없는 경기는 비교에서 빼서 불공정한 비교를 막음 |
| 검증 기준(3c) | 결과별 ECE ≤ 0.03이고 시장 마감 전 배당보다 로그 손실 95% 구간 상한 < 0이어야 VALIDATED. 아니면 NOT_VALIDATED와 사유 문장. 통과 전에는 확률을 보여 주지 않음 |
| 경기 전 예측(3d) | 스냅샷을 찍는 순간에만 만들고, 학습 자료는 실제 수신 시각이 기준 시각 이전인 결과뿐("시작 3시간 뒤" 가정 안 씀). 보류 사유: `MODEL_NOT_VALIDATED`, `LOW_TEAM_HISTORY(<5)`, `INSUFFICIENT_TRAINING_DATA(<100)`, `NO_ACTIVE_MODEL`, `MODEL_CODE_CHANGED`(평가받지 않은 코드), `PREDICTION_FAILED:<오류>` |
| 예측 실패 격리(3d) | 예측은 저장점 안에서 실행. 실패해도 입력 스냅샷은 남고 실패 사유를 기록. 모델 모듈을 불러올 수 없어도 스냅샷은 계속 |
| 검증 설계(3e) | 검증·시험 시즌을 고정해 앞쪽에 자료를 더해도 이미 선택에 쓴 시즌이 시험으로 밀리지 않게 함. 시험 결과를 본 횟수를 문서에 남김 |
| 평가받은 코드인지(3e) | 모델 코드 버전을 3e.1로 올림. 경기 전 예측은 저장된 이름·설정으로 다시 만든 모델의 버전이 평가받은 버전과 같을 때만 확률을 만든다(`MODEL_CODE_CHANGED`) |
| NBA 수집(5d-a) | 키 없으면 `NOT_CONFIGURED`(실패 아님). 429는 60초 뒤 최대 3번, 401·연결 실패는 키 없는 `BalldontlieError`(원래 예외 끊음). cursor가 40쪽을 넘으면 중단. 품질 문제 `MALFORMED_GAME`·`SAME_TEAM`·`INVALID_SCORE`·`TIED_FINAL`(농구는 무승부 없음)·`DUPLICATE_GAME`. 예정 경기의 0점은 NULL. 같은 이름의 축구 팀이 있으면 섞지 않고 실패. DB CHECK: 끝난 경기는 점수가 있고 같지 않음, 예정·연기 경기는 점수 없음 |
| 리그별 모델(5c) | 실행 구분 키에 리그를 넣어 다른 리그 실행이 활성 모델로 섞이지 않게 함. 과거 시장 배당이 검증 예측의 50% 미만이면 시장 결합을 만들지 않고 `NO_MARKET_HISTORY`로 남김. 시장 비교 자료가 없으면 검증 기준을 통과로 처리하지 않음. 리그 모델이 아직 없을 때는 `NO_ACTIVE_MODEL`로 확률 없이 보류 |
| 배당 API(5b) | 키는 URL에 들어가므로 오류에서 지움. 크레딧 예산: 무료 일정 조회로 시각을 보고 24·1시간 전 스냅샷 직전에만 리그별 1크레딧, 90분 안 재조회 금지, 남은 크레딧 60 미만이면 1시간 전만. 1 이하 배당이나 세 결과가 다 없는 북메이커는 버림. 팀 이름은 검토한 대조표로만 연결하고 실패는 `UNMAPPED_TEAM`·`MATCH_NOT_FOUND`로 남김. 배당 수집 실패는 재시도하지 않고(크레딧 보호) 스냅샷은 그대로 찍음 |
| 다중 리그(5a) | 학습·평가한 리그(MODELED)만 예측하고, 나머지는 확률 없이 `LEAGUE_NOT_MODELED`. 팀 대조표는 같은 날짜 경기 근거 90% 이상·겹침 없음일 때만 추가. 수집기는 한 대회가 실패해도 나머지 대회를 계속 조회 |
| 경기 기록(3g) | 슈팅·유효 슈팅·퇴장 열이 없거나 비면 기록 없음(0으로 채우지 않음). 숫자가 아니면 `INVALID_STAT`, 유효 슈팅 > 슈팅이면 `INCONSISTENT_STAT`로 거르고 DB CHECK도 같은 규칙. 실제 원본 오류 1건(2021-08-15 뉴캐슬-웨스트햄) 거름. 시장 결합은 시장 확률이 없으면 확률 없이 `MARKET_ODDS_MISSING` |
| 알림(4b) | 봇 토큰은 URL에 들어가므로 오류 문구에서 지우고 원래 예외를 이어 붙이지 않음(`raise … from None`). 429는 retry_after만큼 대기. 설정이 없으면 NOT_CONFIGURED로 건너뜀. 보낸 알림은 (종류, 키)로 기록해 재시도해도 한 번만(보낸 뒤 기록 = 최소 한 번). 실패 알림 콜백은 예외를 내지 않아 원래 실패를 가리지 않음 |
| 엔진 간 대조(4a) | Spark 결과를 같은 스냅샷의 dbt 결과와 행·열 단위로 대조(pyarrow, Spark 밖에서). 불일치가 하나라도 있으면 종료 코드 1 → 매일 DAG의 `spark_reconcile` 작업 실패(재시도는 S3 일시 오류용 1번만). Spark가 아예 못 뜨면 stderr 끝부분을 오류에 담음. Spark 테스트는 `REQUIRE_SPARK=1`이면 건너뛰지 않고 실패 |
| 선택 낙관 제거(3f) | 보정 계수는 검증 시즌을 서로 바꿔 채점(교차 보정). 검증 시즌이 하나면 같은 자료로 고르고 채점하는 대신 오류 |
| 과신 방지(3c) | 차이의 구간은 주 단위 블록 부트스트랩으로(경기 단위로 뽑으면 구간이 좁아져 과신), 비율 구간은 Wilson(작은 표본에서도 0~1 안) |

## 8. 실제로 겪은 장애와 해결

| # | 문제 | 원인 | 해결 | 배운 점 |

| 1 | MinIO 이미지를 받을 수 없음(Docker Hub 거부, quay.io 401) | MinIO 커뮤니티판 이미지 배포 중단, 저장소 보관 | SeaweedFS로 교체, 클라이언트를 표준 S3 API(boto3)로 | 특정 제품 SDK 대신 표준 API에 맞추면 교체 비용이 작다 |

## 면접에서 나올 만한 질문

**Q. 잘못된 데이터가 들어오면 어떻게 하나요?**
버리지 않고 사유와 함께 별도 테이블에 남깁니다. 수집 단계 문제는 `silver.quality_issues`, 스트리밍 문제는 `silver.stream_rejections`입니다. 그리고 결측을 0으로 채우거나 이름이 비슷한 팀을 추측해 연결하지 않습니다. 마지막 방어선으로 DB의 CHECK 제약과 수정 차단 트리거가 있어, 코드에 실수가 있어도 형식이 틀린 값이나 이력 덮어쓰기는 DB가 거부합니다.

**Q. 두 소스의 값이 다르면 어느 쪽을 믿나요?**
수집 단계에서는 판단하지 않고 둘 다 보존한 뒤 불일치를 기록합니다(`DATE_MISMATCH`, `SCORE_MISMATCH`). 어느 쪽을 쓸지는 Gold에서 규칙으로 정합니다. 갱신 시각을 주는 football-data.org를 우선하고, 없으면 openfootball을 쓰며, 어느 쪽 값인지 열로 남깁니다.

**Q. 가장 어려웠던 버그는요?**
원본이 A → B → A로 되돌아가는 경우입니다. "이미 처리한 원본이면 다시 계산하지 않는다"는 최적화가 있었는데, 원본이 예전 내용으로 돌아가면 그 원본은 이미 본 것이라 건너뛰고, 최신 상태가 B에 머물렀습니다. 통합 테스트로 재현한 뒤, 원본이 같아도 Silver 비교는 항상 하도록 바꿨습니다. 비교 결과가 같으면 버전이 늘지 않으므로 안전합니다.

**Q. 외부 API가 죽으면요?**
일시적 오류(429)만 기다렸다가 재시도하고, 키 문제 같은 영구적 오류는 바로 실패로 기록합니다. 수집기는 한 번 실패해도 프로세스가 살아서 5분 뒤 다시 시도하고, 컨테이너가 죽으면 Docker가 다시 띄웁니다. 다음 조회에서 전체 목록을 다시 받으므로 놓친 갱신을 따라잡습니다.
