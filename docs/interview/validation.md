# 검증 체계: 무엇을, 어떻게 검증하나

작성: 2026-10-21(4a 시점). "이 결과를 어떻게 믿을 수 있나요?"라는 질문에 한 번에 답하기 위한 문서입니다.

## 한눈에 보기

검증은 다섯 층입니다. 아래 층이 깨지면 위 층의 숫자는 의미가 없으므로 아래부터 쌓았습니다.

| 층 | 질문 | 방법 | 결과(2026-10-21) |
|---|---|---|---|
| 1. 데이터 형식 | 들어온 값이 형식에 맞나 | 수집 단계 검사(이유 코드와 함께 걸러 냄) + DB CHECK·UNIQUE·수정 차단 트리거 + dbt 테스트 26개 | dbt PASS=34(모델 8 + 테스트 26), 걸러 낸 레코드 2건 + 경기 기록 원본 오류 1건(3g) |
| 2. 시점 누수 | 미래 정보가 섞이지 않았나 | 기준 시각 함수(`*_known_at`), dbt 누수 테스트, Python 독립 재계산, 백테스트 예측의 DB CHECK, 경기 전 예측의 외래 키 | 독립 재계산 2,660경기 불일치 0, 누수 CHECK 위반 0 |

| 4. 모델 성능 | 모델이 쓸 만한가 | 시간순 백테스트, 검증·시험 시즌 분리, 블록 부트스트랩 95% 구간, 확률 보정(ECE), 검증 기준 | 모든 모델 NOT_VALIDATED(시장보다 확실히 부정확) |
| 5. 운영 성능 | 실제로 그 시점에 맞혔나 | 경기 전 스냅샷 순간의 예측 기록(PROSPECTIVE) + 매주 채점 | 첫 기록 10/22 19:00 UTC부터 쌓임 |

## 1. 데이터 형식

- **수집 단계:** 형식이 틀린 레코드는 버리지 않고 이유 코드와 함께 `silver.quality_issues`에 남깁니다. 스트리밍은 `silver.stream_rejections`에 남깁니다.
- **DB 제약:** 점수 0 이상, 배당 > 1, 홈 ≠ 원정 같은 CHECK, 중복을 막는 UNIQUE, 이력을 덮어쓰지 못하게 하는 트리거가 있습니다. 코드에 실수가 있어도 DB가 거부합니다.
- **dbt 테스트:** 유일성, 필수값, 허용값, 순위표 정합성, 확률 합 = 1. 하나라도 실패하면 빌드가 실패합니다.
- **외부 대조:** 2024-25 순위표를 공개된 순위표와 비교했습니다(리버풀 84점 등 일치). 두 소스 사이의 날짜·점수 불일치는 0건이었습니다.

## 2. 시점 누수

예측에서 가장 위험한 실수라 여러 겹으로 막았습니다.

| 장치 | 어디서 |
|---|---|
| 기준 시각 함수: 발표·수신 시각이 모두 기준 시각 이전인 버전만 | `silver.*_known_at(as_of)` |
| 학습 데이터셋: 특징에 쓴 가장 최근 경기도 시작 + 3시간 ≤ 대상 시작 | dbt 테스트 `assert_features_use_only_prior_results` |
| 같은 규칙을 Python으로 다시 계산해 비교 | `pipelines/modeling/dataset.py`의 `verify_point_in_time` |
| 백테스트 예측: 학습에 쓴 마지막 경기 + 3시간 ≤ 학습 기준 시각 ≤ 경기 시작 | `modeling.backtest_predictions`의 CHECK |
| 경기 전 예측: 기준 시각이 스냅샷과 정확히 같아야 함, 기록 시각은 그 뒤 10분 안 | `snapshots.prematch_predictions`의 외래 키·CHECK |
| 마감 배당은 입력으로 쓰지 않고 비교 기준으로만 | 3a 설계 |

## 3. 구현 동등성

같은 규칙을 서로 다른 코드로 구현해 대조합니다. 한 구현만 있으면 그 구현의 버그를 잡을 방법이 없기 때문입니다.

```text
           dbt(SQL, LATERAL)
             ↗           ↖
  대조(pyarrow)          누수 검사(3a)
         ↙                    ↘
Spark(조인 + 창 함수) ← 단위 테스트 정답 → Python 독립 재계산
```

- **dbt ↔ Python**(3a): 2,660경기 × 양 팀 × 특징 7개, 불일치 0.
- **dbt ↔ Spark**(4a): 2,660경기 × 18개 열, 불일치 0. 대조 코드 자체도 값 하나를 바꾸면 그 칸 하나만 잡는지 테스트했습니다.
- **Spark ↔ Python**(4a 단위 테스트): 3시간 경계, 대상 경기 제외, 최근 10경기만.
- **모델 코드 변경 전후**(3e): 새 옵션을 끈 모델이 이전 코드와 확률이 완전히 같았습니다.

## 4. 모델 성능

| 원칙 | 방법 |
|---|---|
| 미래로 학습하지 않는다 | 매주 그 주 첫 경기 시작 시각에 알려진 결과로만 다시 학습(walk-forward) |
| 시험은 한 번만 | 설정은 검증 시즌(2021-22·2022-23)에서만 고르고, 시험 시즌(2023-24 이후)은 고른 설정으로 평가. 시험 결과를 본 횟수도 기록(3e에서 3번) |
| 고른 자료로 채점하지 않는다 | 보정 계수는 시즌을 서로 바꿔 채점(교차 보정, 3f) |
| 기준선과 비교한다 | 단순 비율, 시장 마감 전·마감 배당 |
| 우연인지 확인한다 | 주 단위 블록 부트스트랩 95% 구간. 같은 주 경기는 독립이 아니라 경기 단위로 뽑으면 구간이 좁아진다 |
| 확률을 믿을 수 있나 | 구간별 실제 비율(Wilson 구간), 결과별 ECE |
| 통과 기준을 미리 정한다 | 결과별 ECE ≤ 0.03이고 시장 마감 전 배당보다 로그 손실 95% 구간 상한 < 0일 때만 VALIDATED |

지금 결과: 가장 좋은 모델도 시장 마감 전 배당보다 로그 손실이 약 0.017 나쁘고, 95% 구간이 0을 넘지 않습니다. 그래서 모든 모델이 NOT_VALIDATED이고 예측은 WITHHELD입니다.

5e부터 주간 보고서가 NBA 경기 전 확률을 같은 시점의 해외 시장 확률과 함께 채점합니다(과거 배당이 없는 종목의 검증 경로). 5d-c부터는 NBA에도 같은 기준을 적용합니다. NBA 모델은 보정 기준(ECE ≤ 0.03)은 통과했지만, 과거 NBA 배당이 없어 시장 비교를 할 수 없으므로 NOT_VALIDATED입니다. 5c부터는 다섯 리그 각각에 같은 기준을 적용합니다. 새 네 리그는 과거 시장 배당이 없어 "시장보다 나은가"를 판단할 수 없으므로 통과로 처리하지 않고 사유를 남깁니다.


3g에서 시장 배당과 모델을 섞어 보니 두 검증 시즌 모두 "시장 100%"가 골라졌습니다. 공개 통계(점수·슈팅·퇴장·휴식)로 만든 모델은 시장에 없는 정보를 거의 갖고 있지 않다는 뜻이고, 이것도 검증으로 얻은 결론입니다.

## 5. 운영 성능

- 과거 재구성은 "결과는 시작 3시간 뒤 공개"라는 가정 위에 있습니다. 실제 수집 지연이나 PC가 꺼진 시간은 재현하지 못합니다.
- 그래서 경기 24·3·1시간 전 스냅샷을 찍는 순간, 그때까지 실제로 받은 자료만으로 예측을 함께 저장합니다. 나중에 채워 넣을 수 없게 DB가 막습니다.
- 매주 화요일 채점하고, 놓친 시점(MISSED)과 보류율도 함께 보고합니다.
- 시험 시즌은 개발 중에 몇 번 봤기 때문에, 이 기록이 진짜 처음 보는 평가입니다. 결론을 내리려면 300경기 이상(거의 한 시즌)이 필요합니다.

## 면접에서 나올 만한 질문

**Q. 이 예측 결과를 어떻게 믿을 수 있나요?**
아직 믿으면 안 된다는 것까지 검증했습니다. 데이터 형식, 시점 누수, 구현 동등성은 통과했습니다. 하지만 모델 성능은 시장 배당보다 확실히 부정확하다고 나와서, 미리 정한 기준에 따라 확률을 보여 주지 않습니다. 실제 성능은 경기 전에 남긴 기록으로 매주 쌓아 가며 봅니다.

**Q. 검증에서 가장 중요하게 생각한 건요?**
검사하는 쪽이 검사받는 쪽에 기대지 않는 것입니다. 같은 규칙을 다른 코드·다른 엔진으로 구현해 대조하고, 대조 코드 자체도 일부러 틀린 값을 넣어 잡아내는지 테스트했습니다. 그리고 결과를 보기 전에 통과 기준을 정해 두었습니다.
