# 2d. 과거 시즌 재생기

작성: 2026-10-21. 이 단계의 커밋: `f6e72a0`(구현), `ccab9e2`(재생 토픽 삭제를 기다리도록 수정).

## 한 줄 요약

지난 시즌 경기를 "일정 발표 → 결과" 이벤트로 시간 순서대로 다시 흘려 보내면서, 일부러 중복과 늦은 도착을 섞습니다. 그다음 별도 DB에 쌓인 최종 상태가 원본과 한 경기도 다르지 않은지 자동으로 검사합니다. 2c 소비자가 실제 장애 상황에서도 맞게 동작하는지 증명하는 도구입니다.

## 왜 필요한가

2c의 테스트는 경기 몇 개로 규칙을 확인합니다. 하지만 "시즌 전체 규모에서, 장애가 여기저기 섞여도 최종 결과가 맞는가"는 따로 보여 줘야 합니다. 실제 운영에서는 장애를 원하는 때에 일으킬 수 없으므로, 과거 데이터를 다시 흘리면서 장애를 일부러 넣는 방법을 씁니다. 같은 시드를 쓰면 매번 똑같은 장애가 나서 결과를 비교할 수 있습니다.

## 흐름

```text
replay_season("2025-26")
 ├ 1. 재생 DB(sports_replay)를 지우고 새로 만든다   실제 DB(sports)는 읽기만 한다
 ├ 2. season_events                               원본 DB의 openfootball 경기마다 이벤트를 만든다
 │     - 일정 발표: published_at = 경기 7일 전, 상태 SCHEDULED
 │     - 결과:     published_at = 경기 시작 3시간 후, 상태 FINISHED(끝난 경기만)
 ├ 3. 발표 시각 순서로 정렬
 ├ 4. inject_faults(시드 고정)
 │     - 중복: 일부 이벤트를 한 번 더 끼워 넣는다
 │     - 늦은 도착: 일부 "일정 발표"를 그 경기 결과보다 뒤로 옮긴다
 ├ 5. 재생 토픽(replay.matches.v1)을 지우고 다시 만든 뒤 전부 보낸다
 ├ 6. 2c 소비자(match_consumer.run)를 새 그룹으로 돌려, 새 메시지가 없을 때까지 재생 DB에 반영
 └ 7. 경기별 최종 상태(상태·점수)를 원본과 비교 → mismatches(불일치 수)
```

## 설계 결정과 이유

| 결정 | 위치 | 이유 |
|---|---|---|
| 재생 DB를 매번 지우고 새로 만듦 | `recreate_database` (replay.py:84) | 지난 재생 결과가 남아 있으면 이번 결과가 달라진다. 실제 DB 이름이 들어오면 거부한다 |
| 실제 DB는 읽기만 | `replay_season` (:94) | 검증 도구가 운영 데이터를 바꾸면 안 된다. 2026-10-21 확인에서 재생 전후 실제 DB 체크섬이 같았다 |
| 발표 시각: 일정 7일 전, 결과 시작 3시간 후 | `ANNOUNCE_BEFORE`, `RESULT_AFTER` (:32, :33) | 과거 자료에는 발표 시각이 없다. docs/football_data_sources.md의 과거 재구성 가정(시작 + 3시간)과 맞췄다 |
| 장애를 시드로 고정 | `inject_faults`의 `random.Random(seed)` (:68) | 같은 시드면 같은 장애가 나서, 코드를 바꾼 뒤 결과를 그대로 비교할 수 있다 |
| 늦은 도착은 "일정 발표"를 결과 뒤로 옮김 | `inject_faults` (:66) | 가장 위험한 경우다. 그냥 저장하면 끝난 경기가 "예정"으로 되돌아간다 |
| 재생 토픽도 지우고 다시 만듦 | `replay_season` | 지난 재생의 메시지가 섞이지 않게. 삭제가 끝날 때까지 기다린다(2a의 `delete_topics`) |
| 2c 소비자를 그대로 재사용 | `match_consumer.run` 호출 | 재생용으로 따로 만든 코드가 아니라 실제 운영 소비자를 검증해야 의미가 있다 |
| 결과를 숫자 하나로 판정 | `mismatches` (:135) | 0이면 통과. 명령 종료 코드도 0/1이라 CI나 스크립트에서 바로 쓸 수 있다 |

## 2026-10-21 확인 결과 (2025-26 시즌, 380경기, 이벤트 760개)

| 실행 | 보낸 메시지 | 섞은 중복 | 섞은 늦은 도착 | 소비자 결과 | 불일치 |
|---|---|---|---|---|---|
| 기본(시드 7, 중복 10%, 늦은 도착 5%) | 837 | 77 | 19 | 저장 741, 중복 77, 늦은 도착 거부 19 | 0 |
| 같은 설정으로 한 번 더 | 837 | 77 | 19 | 위와 똑같음 | 0 |
| 장애를 많이(시드 42, 중복 50%, 늦은 도착 50%) | 1,031 | 271 | 185 | 저장 575, 중복 271, 늦은 도착 거부 185 | 0 |

숫자 읽는 법:

- 보낸 메시지 = 이벤트 760 + 중복. 늦은 도착은 추가가 아니라 순서를 옮긴 것이다.
- 저장 = 760 − 늦은 도착. 늦게 온 일정 발표는 결과보다 오래된 정보라 저장되지 않아야 맞다.
- 섞은 중복 수와 소비자가 건너뛴 수, 섞은 늦은 도착 수와 소비자가 거부한 수가 정확히 같다.
- 세 번 모두 실제 DB(경기 버전 2,280행, 실시간 380행, 배당 166,589행)의 행 수와 체크섬이 재생 전후로 같았다.

## 직접 확인하는 방법

기본 설정으로 재생(1~2분 걸림, 마지막 줄의 `"mismatches": 0`을 확인):

```bash
.\.venv\Scripts\python.exe -m pipelines.streaming.replay --season 2025-26
```

장애를 더 많이 섞어 보기:

```bash
.\.venv\Scripts\python.exe -m pipelines.streaming.replay --season 2025-26 --seed 42 --duplicate-rate 0.5 --late-rate 0.5
```

다른 시즌(2021-22 ~ 2025-26)도 같은 방식으로 재생할 수 있습니다.

테스트:

```bash
.\.venv\Scripts\python.exe -m pytest tests/test_streaming_unit.py tests/test_streaming_integration.py -q -k "inject_faults or replay"
```

## 테스트가 확인하는 것

|---|---|

## 면접에서 나올 만한 질문

**Q. 스트리밍 처리가 맞다는 걸 어떻게 증명했나요?**
과거 시즌 760개 이벤트를 시간 순서로 다시 흘리면서 중복과 순서 뒤바뀜을 일부러 넣었습니다. 그다음 결과 DB의 경기별 최종 상태를 원본과 비교했습니다. 중복과 늦은 도착을 절반씩 섞은 경우에도 380경기 모두 일치했고, 소비자가 건너뛰거나 거부한 수가 넣은 장애 수와 정확히 같았습니다.

**Q. 왜 시드를 고정했나요?**
같은 장애를 다시 만들기 위해서입니다. 코드를 고친 뒤 같은 시드로 돌려 결과가 바뀌는지 비교할 수 있고, 실패하면 그 실패를 그대로 재현할 수 있습니다.

**Q. 운영 데이터는 안전한가요?**
재생은 별도 DB(sports_replay)를 매번 새로 만들어 쓰고, 실제 DB는 읽기만 합니다. 실제 DB 이름이 재생 대상으로 들어오면 코드가 거부합니다. 재생 전후 실제 DB 체크섬이 같은 것도 확인했습니다.

**Q. 실제 운영과 무엇이 다른가요?**
과거 자료에는 발표 시각이 없어 "일정은 7일 전, 결과는 시작 3시간 후"라고 가정했습니다. 또 메시지는 한꺼번에 빠르게 보내므로 실제 시간 간격은 재현하지 않습니다. 검증하려는 것은 시간 간격이 아니라 순서와 중복에 대한 처리 규칙입니다.

## 한계

- 점수 정정(같은 경기의 점수가 나중에 바뀌는 경우)은 섞지 않습니다. 원본에 정정 이력이 있으면 그 버전들도 이벤트로 만들도록 확장할 수 있습니다.
- 재생은 openfootball 기준 이벤트만 만듭니다. football-data.org 형식의 이벤트는 2c 테스트에서 따로 확인합니다.
- 재생 DB에는 Gold를 만들지 않습니다. 필요하면 dbt를 `DBT_POSTGRES_DB=sports_replay`로 돌릴 수 있습니다.
- 재생 토픽에는 마지막 재생의 메시지가 남아 있습니다(다음 재생 때 지우고 다시 만듦).
