# 4b. 텔레그램 알림: 휴대폰으로 경기 전 기록·주간 채점·장애 받기

작성: 2026-10-21.

## 한 줄 요약

집 PC로 들어오는 길(포트, VPN)을 만들지 않고, PC가 텔레그램으로 **내보내는** 방식으로 휴대폰에서 결과를 봅니다. 경기 전 스냅샷, 주간 채점 보고서, Airflow 작업 실패를 내 대화방으로 보내고, 보낸 기록을 DB에 남겨 같은 알림이 두 번 가지 않게 했습니다. 봇 토큰을 넣으면 바로 동작합니다(아래 "설정 방법").

## 왜 이 방식인가

밖에 있는 휴대폰이 집 PC의 데이터를 보려면, 보통은 집 PC로 들어오는 길이 있어야 합니다. 포트를 열면 자동 스캐너가 금방 찾아내고, VPN은 별도 설정이 필요합니다. 반대로 PC가 결과를 밖으로 내보내면 들어오는 길이 필요 없습니다.

| 방식 | 판단 |
|---|---|
| **텔레그램 봇(선택)** | 포트·VPN 없음, 알림이 바로 옴, 이미 쓰고 있는 앱 |
| Tailscale | 화면을 제대로 보려면 좋지만 설정할 것이 있음. 나중에 웹 화면을 만들면 함께 쓸 수 있음 |
| 포트 열기 | 하지 않음 |

## 무엇을 보내나

| 알림 | 언제 | 내용 |
|---|---|---|
| 경기 전 스냅샷 | 30분마다 스냅샷 DAG 뒤(새 기록이 있을 때만) | 경기(한국 시각), 시점별 찍음·놓침, 예측 상태. **검증 기준을 통과한 예측만 확률을 보내고**, 지금처럼 보류 중이면 "예측 보류(모델 미검증)"만 보냄 |
| 주간 보고서 | 화요일 06:00 UTC(한국 15:00) 주간 DAG 뒤 | 시점별 찍음·놓침, 채점 경기 수, 로그 손실과 시장 비교, 누적, 보류 사유 |
| 작업 실패 | Airflow 작업이 마지막 재시도까지 실패했을 때 | DAG·작업 이름, 실행 ID, 오류 앞부분(토큰은 지움) |

메시지 예:

```text
⚽ 경기 전 스냅샷 2건

10/24(토) 20:30 Aston Villa FC vs Manchester City FC
· 24시간 전: 찍음 · 예측 보류(모델 미검증)
· 3시간 전: 놓침(그 시각에 기록하지 못함)
```

## 설계 결정과 이유

| 결정 | 위치 | 이유 |
|---|---|---|
| 표준 라이브러리(urllib)로 Bot API 호출 | `pipelines/notify/telegram.py` | 의존성을 늘리지 않는다. 기존 football-data.org 수집기와 같은 방식(호출 함수를 바꿔 끼워 테스트) |
| 토큰을 오류·로그에서 지움 | `redact`, `raise … from None` | Bot API는 토큰이 URL 경로에 들어간다. 원래 예외를 이어 붙이면 traceback에 URL이 남을 수 있어 끊는다 |
| 4096자 넘으면 줄 단위로 나눔 | `split_message` | 텔레그램 메시지 한 개의 한도 |
| 429는 retry_after만큼 기다림 | `call` | 텔레그램이 알려 주는 대기 시간을 따른다 |
| 설정이 없으면 NOT_CONFIGURED | `send` | 알림은 선택 기능이다. 토큰이 없어도 파이프라인은 그대로 돈다 |
| 보낸 기록을 DB에 | `pipelines/sql/008_notifications.sql`, `alerts.deliver` | DAG가 재시도하거나 다시 돌아도 같은 알림을 다시 보내지 않는다. 본문은 저장하지 않고 해시만 남긴다 |
| 보낸 뒤 기록(최소 한 번) | 같은 함수 | 기록이 먼저면 보내기에 실패했을 때 영영 안 간다. 보낸 직후 기록이 실패하면 한 번 더 갈 수 있다(중복 한 번이 누락보다 낫다) |
| 오래된 기록은 알리지 않음 | `PREMATCH_LOOKBACK`(48시간), `PREMATCH_STALE_AFTER`(경기 시작 24시간 뒤) | 처음 설정했을 때 지난 주말 경기의 "놓침" 30건이 한꺼번에 오지 않게(실제 DB로 확인: 0건) |
| 알림은 별도 작업 | 스냅샷·주간 DAG의 `notify_*` 작업 | 알림이 실패해도 스냅샷·보고서는 이미 저장돼 있다 |
| 실패 알림 콜백은 예외를 내지 않음 | `airflow_failure_callback` | 알림 실패가 원래 실패를 가리면 안 된다 |
| 검증 전 확률은 보내지 않음 | `prematch_text` | 화면에 보여 주지 않는 원칙(WITHHELD)을 휴대폰에도 똑같이 적용 |

## 설정 방법(직접 하실 일)

1. **봇 만들기:** 텔레그램에서 `@BotFather`를 찾아 대화를 열고 `/newbot` → 봇 이름(아무거나, 예: `Sports Prediction`) → 봇 아이디(`bot`으로 끝나야 함, 예: `seol_sports_pred_bot`). 마지막에 받은 **토큰**(`123456789:AA…` 형태)을 복사합니다.
2. **토큰 넣기:** 프로젝트의 `.env` 파일에 `TELEGRAM_BOT_TOKEN=받은토큰` 한 줄을 추가합니다. 토큰은 비밀번호와 같으니 다른 곳에 붙여 넣지 마세요.
3. **봇에게 말 걸기:** 텔레그램에서 방금 만든 봇을 찾아 `/start` 또는 아무 메시지를 보냅니다. 봇이 내 대화방을 알게 하는 단계입니다.
4. **대화방 ID 확인:** `.\.venv\Scripts\python.exe -m pipelines.notify.telegram chat-id`를 실행하면 `chat_id`가 나옵니다. 이것을 `.env`에 `TELEGRAM_CHAT_ID=숫자`로 추가합니다.
5. **시험 메시지:** `.\.venv\Scripts\python.exe -m pipelines.notify.telegram test` → 휴대폰에 시험 메시지가 오면 성공입니다.
6. **Airflow에 반영:** Airflow 컨테이너가 새 설정을 읽도록 다시 띄웁니다: `docker compose --env-file .env -f infra/docker-compose.yml --profile airflow up -d airflow`

2~6번은 말씀해 주시면 제가 해도 됩니다(토큰 값은 보거나 출력하지 않습니다).

기존 봇을 써도 보내는 것은 되지만 새 봇을 추천합니다. 토큰을 따로 관리할 수 있고(새거나 바꿔도 기존 봇에 영향 없음), 대화방이 섞이지 않고, 기존 봇이 메시지를 받는 방식(getUpdates·웹훅)과 4번의 대화방 ID 확인이 충돌하지 않습니다.

## 면접에서 나올 만한 질문

**Q. 휴대폰에서 집 서버 데이터를 어떻게 봤나요?**
들어오는 길을 만들지 않고 내보내는 방식을 택했습니다. 포트를 열면 보안 부담이 크고 VPN은 설정이 필요한데, 제가 휴대폰으로 볼 것은 경기 전 기록과 주간 채점 정도라 텔레그램 메시지로 충분했습니다. 서버는 계속 127.0.0.1에만 열려 있습니다.

**Q. 알림이 중복되거나 빠지지 않게 어떻게 했나요?**
보낸 알림을 (종류, 키)로 DB에 기록해 재시도나 재실행에도 다시 보내지 않습니다. 순서는 "보낸 뒤 기록"이라 최소 한 번입니다. 기록을 먼저 하면 전송 실패 시 영영 빠지고, 지금 방식은 최악의 경우 한 번 중복입니다. Kafka 소비자에서 "DB 커밋 뒤 오프셋 커밋"을 택한 것과 같은 판단입니다.

**Q. 봇 토큰은 어떻게 보호했나요?**
`.env`에만 두고 Git에서 제외했습니다. Bot API는 토큰이 URL에 들어가서, 오류 메시지에서 토큰을 지우고 원래 예외를 이어 붙이지 않게 해서 traceback에도 남지 않게 했습니다. 이 부분을 테스트로 확인합니다.

## 한계

- **아직 실제로 보내 보지 않았습니다.** 봇 토큰을 넣은 뒤 시험 메시지로 확인해야 합니다.
- **메시지가 텔레그램 서버를 거칩니다.** 봇 메시지는 종단 간 암호화가 아닙니다. 보내는 내용은 경기 일정과 모델 상태라 민감도는 낮습니다.
- **조회는 안 되고 받기만 합니다.** "지금 상태 보여 줘" 같은 명령에 답하는 기능은 없습니다(필요하면 다음 단계).
- **PC가 꺼져 있으면 알림도 없습니다.** 놓친 시점은 PC가 켜진 뒤 "놓침"으로 알립니다(경기 시작 24시간 안이면).
