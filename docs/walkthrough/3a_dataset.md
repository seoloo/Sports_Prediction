# 3a. 시간순 학습·평가 데이터셋

작성: 2026-10-21. 이 단계의 커밋: `1d5c999`.

## 3단계 전체 계획

| 단위 | 내용 | 상태 |
|---|---|---|
| **3a** | 시간순 학습 데이터셋: 경기마다 시작 전에 알 수 있던 팀 지표, 시장 기준선, 결과. 미래 정보 누수 자동 검사 | 완료 |
| 3b | 기준 모델: 단순 비율 → Poisson → Dixon-Coles를 시즌 순서대로 학습·평가 | 다음 |
| 3c | 평가 보고서: 로그 손실·Brier, 확률 보정, 시장 배당 대비 차이와 불확실성 | 예정 |
| 3d | 경기 전 스냅샷(2e)에 모델 확률을 붙이고 경기 후 채점하는 주간 보고서 | 예정 |

## 한 줄 요약

경기마다 "그 경기 시작 전에 알 수 있었던 결과만으로" 팀 지표를 계산해 한 행으로 묶은 데이터셋(`gold.match_features_pit`)입니다. 결과와 시장 배당 기준선도 함께 들어 있어, 3b 모델이 이 표 하나로 학습하고 평가합니다.

## 왜 이게 가장 중요한가

스포츠 예측에서 가장 흔한 실수는 미래 정보가 학습에 섞이는 것입니다. 예를 들어 시즌 전체 평균 득점을 특징으로 쓰면, 시즌 초반 경기의 특징에 그 뒤 경기 결과가 들어갑니다. 그러면 백테스트 성능은 좋게 나오지만 실제로는 쓸 수 없습니다. 그래서 모델보다 먼저 "누수 없는 데이터셋"을 만들고, 누수가 없다는 것을 두 가지 방식으로 검사합니다.

## 과거 재구성 가정

과거 시즌 결과는 모두 이번 주(10/20)에 한꺼번에 수집했습니다. 그래서 1·2단계의 원칙("우리가 실제로 받은 시각 이전 자료만")을 그대로 적용하면, 과거 경기에는 쓸 수 있는 자료가 하나도 없습니다. 그래서 1단계 문서(docs/football_data_sources.md)에서 미리 정한 가정을 씁니다.

- **결과는 경기 시작 3시간 뒤에 알려졌다.** 경기 M의 특징에는 시작 + 3시간 ≤ M의 시작인 경기만 들어갑니다.
- 이 가정은 데이터셋의 `mode = HISTORICAL_RECONSTRUCTION`, `availability_rule` 열에 남깁니다.
- 실제로 경기 전에 저장한 기록(2e 스냅샷, PROSPECTIVE)과는 따로 평가하고 따로 보고합니다.

## 데이터셋 열

| 묶음 | 열 | 뜻 |
|---|---|---|
| 경기 | `match_id`, `season`, `kickoff_utc`, `home_team`, `away_team` | 대상 경기 |
| 팀 지표(홈·원정 각각) | `*_l10_n`, `*_l10_gf`, `*_l10_ga`, `*_l10_pts` | 최근 10경기: 실제로 쓴 경기 수, 평균 득점·실점·승점 |
| | `*_l38_n`, `*_l38_gf`, `*_l38_ga` | 최근 38경기(약 한 시즌): 경기 수, 평균 득점·실점 |
| | `*_rest_days` | 직전 경기 뒤 쉰 날 수 |
| | `*_last_feature_kickoff` | 특징에 쓴 가장 최근 경기의 시작 시각(누수 검사용) |
| 시장 기준선 | `market_pre_*`, `market_close_*` | 시장 평균 배당의 마진을 뺀 확률(마감 전, 마감) |
| 정답 | `status`, `ft_home`, `ft_away`, `result` | 결과(HOME, DRAW, AWAY). 아직 안 열린 경기는 비어 있음 |
| 가정 | `mode`, `availability_rule` | 과거 재구성 가정 |

마감 배당은 경기 직전 정보(라인업, 마지막 뉴스)까지 담고 있어, 모델 입력으로 쓰면 누수입니다. 비교 기준으로만 씁니다.

## 설계 결정과 이유

| 결정 | 위치 | 이유 |
|---|---|---|
| 특징은 SQL(dbt)로, 팀별 최근 경기를 `LATERAL`로 고름 | `dbt/models/gold/match_features_pit.sql` | 경기마다 "그 시점 이전 경기 중 최근 N개"를 고르는 일을 DB 안에서 한 번에 처리. 2,280행이 3초 |
| 3시간 가정을 한곳에 | 같은 파일의 `availability_lag` | 가정을 바꾸면 한 줄만 고치면 된다 |
| 최근 10경기와 38경기 두 창 | 같은 파일 | 10경기는 최근 흐름, 38경기는 한 시즌 수준의 전력 |
| 쓴 경기 수(`*_n`)도 열로 | 같은 파일 | 시즌 초·승격 팀처럼 기록이 적은 경우를 모델이 알 수 있게. 평균만 있으면 1경기 평균과 10경기 평균을 구분할 수 없다 |
| 시작 시각 없는 경기는 제외 | `where kickoff_utc is not null` | 시작 시각이 없으면 "시작 전"을 정할 수 없다 |
| 누수 검사 1: dbt 테스트 | `dbt/tests/assert_features_use_only_prior_results.sql` | 특징에 쓴 가장 최근 경기도 시작 + 3시간 ≤ 대상 시작인지, 경기 수 범위가 맞는지 |
| 누수 검사 2: Python으로 다시 계산 | `pipelines/modeling/dataset.py`의 `verify_point_in_time` | dbt와 다른 코드로 같은 규칙을 구현해 결과를 비교한다. 같은 SQL로만 검사하면 SQL의 실수를 못 잡는다 |

- 매 시즌 승격 팀은 첫 경기에 기록이 0경기입니다. 2부 리그 데이터가 없기 때문입니다. 모델은 기록이 적을 때 리그 평균 쪽으로 당겨 주는 방식(축소 추정)이 필요합니다.

## 면접에서 나올 만한 질문

**Q. 미래 정보 누수를 어떻게 막았나요?**
경기마다 "그 경기 시작 전에 결과가 알려진 경기"만으로 특징을 계산했습니다. 과거 자료는 발표 시각이 없어 결과가 시작 3시간 뒤에 알려졌다고 가정했고, 그 가정을 데이터셋 열에 남겼습니다. 검사는 두 겹입니다. dbt 테스트가 특징에 쓴 가장 최근 경기의 시각을 확인하고, 별도로 Python이 같은 규칙을 다른 코드로 다시 계산해 2,280행 전부를 비교했습니다. 불일치는 0이었습니다.

**Q. 왜 3시간인가요?**
축구 경기는 보통 2시간 안에 끝나고 결과가 바로 공개됩니다. 3시간은 그보다 여유를 둔 보수적인 값입니다. 중요한 건 이 값이 가정이라는 점을 숨기지 않는 것이라, 열로 남기고 실제 경기 전 기록(PROSPECTIVE) 평가와 분리했습니다.

**Q. 마감 배당을 특징으로 쓰면 더 좋지 않나요?**
성능은 좋아지겠지만, 마감 배당은 경기 직전에야 알 수 있습니다. 경기 전 예측의 입력으로 쓰면 누수입니다. 대신 모델이 넘어야 할 기준선으로 씁니다. 시장 마감 확률의 로그 손실이 0.958이라, 모델이 이보다 낮아야 의미가 있습니다.

**Q. 데이터가 적은 팀은요?**
승격 팀은 첫 경기에 기록이 0입니다. 그래서 평균과 함께 실제로 쓴 경기 수를 열로 남겼습니다. 모델(3b)에서는 기록이 적을수록 리그 평균 쪽으로 당겨 주는 방식을 쓸 계획입니다.

## 한계

- 과거 재구성 가정(시작 + 3시간)은 실제 수집 지연을 재현하지 않습니다. 그래서 운영 성능은 2e 스냅샷으로 따로 평가합니다.
- 특징은 득점·실점·승점 기반의 단순 지표입니다. 슈팅·기대득점(xG)·라인업은 아직 없습니다(xG는 football-data.co.uk 2026-27 원본에만 있음).
- 홈·원정을 나누지 않은 최근 경기 기준입니다. 홈 이점은 3b 모델이 따로 추정합니다.
- 2부 리그 기록이 없어 승격 팀의 초반 지표가 비어 있습니다.
