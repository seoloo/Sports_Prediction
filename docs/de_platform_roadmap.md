# 해외축구 데이터 플랫폼 로드맵 v1


## 목표

1. 데이터 엔지니어링 포트폴리오: 배치·스트리밍 수집, 데이터 레이크, 품질 검증, 오케스트레이션, 컨테이너 배포를 실제 도메인 문제로 보여줍니다.
3. 모바일 확인: 휴대폰에서 예측과 기록을 조회합니다. 외부 접속 방식은 4단계에서 별도로 결정합니다.

## 바꾸지 않는 원칙

- published_at, received_at, as_of에 따른 시점 선택과 누수 방지
- 덮어쓰지 않는 버전 저장, 원본 해시와 수집 이력 보존
- 사용권 검토 전 소스 비활성, 목적별 사용권 구분
- 자료·규칙·모델 검증이 부족하면 WITHHELD와 이유 표시
- 서비스는 기본적으로 127.0.0.1에만 바인딩

기존 `src/`의 검증·규칙·시점 로직은 도메인 핵심으로 재사용합니다. 기존 Streamlit 앱과 SQLite는 4단계 서빙 전환 전까지 그대로 동작합니다.

## 목표 구조

```text
openfootball(CC0) ──자동 수집──┐
football-data.co.uk CSV ─수동 다운로드→ landing 폴더 ─┤
football-data.org API ──폴링(2단계)── Kafka ─┤
                                         ↓
                Bronze: S3 호환 저장소(SeaweedFS) 원본(파일 그대로 + 해시·received_at)
                                         ↓
                Silver: 정규화 경기·결과 버전, 팀 별칭 매핑(Postgres)
                                         ↓
                Gold: 시점 기준 특징·백테스트 데이터셋(dbt / Spark)
                                         ↓
                모델 학습·평가 → 예측 스냅샷 → API·화면
Airflow가 전체 작업 순서와 재시도를 관리합니다.
```

## 기술 선택과 이유

| 역할 | 선택 | 이유 |
|---|---|---|
| 운영·분석 DB | PostgreSQL 16 | 버전 테이블, 트리거, 제약을 그대로 옮길 수 있고 dbt·Airflow와 호환 |
| 원본 저장 | SeaweedFS(S3 호환) | Bronze 원본을 내용 해시 경로로 보존. 코드는 표준 S3 API(boto3)만 써서 AWS S3 등으로 그대로 이전 가능. 처음 계획한 MinIO는 커뮤니티판 Docker 이미지 배포가 중단되고 저장소가 보관(archived)되어 2026-10-20에 교체. Parquet·테이블 형식(Iceberg)은 Gold·Spark 단계에서 도입 |
| 스트리밍 | Apache Kafka(KRaft 모드) | 결과 정정·배당 변경·일정 변경을 추가 전용 이벤트로 다룸. 과거 시즌 재생으로 스트리밍 처리 검증 |
| 대용량 처리 | Apache Spark | 여러 리그·시즌 재처리, StatsBomb 이벤트 수준 데이터(연구 전용) 처리 |
| 변환·품질 | dbt + 테스트 | Gold 모델 정의와 품질 검사를 코드로 관리 |
| 오케스트레이션 | Apache Airflow | 수집→정제→특징→학습→평가 순서, 재시도, 백필 |
| 실행 환경 | Docker Compose → kind/k3d 쿠버네티스 + Helm | 로컬 개발은 Compose, 마지막에 배포 구성 시연 |
| CI | GitHub Actions | 단위 테스트, 린트, 소규모 통합 테스트 |

데이터 양이 작은 단계에서는 Spark를 쓰지 않습니다. 각 도구는 필요가 생긴 단계에서 추가합니다.

## 단계

| 단계 | 결과물 | 완료 기준 | 사용자 선행 조건 |
|---|---|---|---|
| 0. 소스 검토 | 소스 검토 문서, 이 로드맵 | 소스별 역할·제약 기록 | 없음 |
| 1a. 로컬 인프라 ✅ | docker-compose(Postgres, SeaweedFS S3), 127.0.0.1 바인딩, `.env.example`, 무작위 비밀번호 생성 | `docker compose up` 후 상태 확인 통과 | 없음 |
| 1b. openfootball 배치 수집 ✅ | Bronze 원본 저장, Silver 경기·결과 버전, 형식 차이 처리, 팀 별칭 | 중복 수집이 멱등, 결측 전반 점수 보존, 재수집 시 변경만 새 버전 | 없음 |
| 1c. 배당 수집 ✅ | landing 폴더의 football-data.co.uk CSV를 Bronze·Silver로 | 수동 다운로드 파일만 처리, 원본 Git 제외 | CSV 수동 다운로드 |
| 1d. 품질·오케스트레이션 ✅ | dbt 모델과 테스트, Airflow DAG, CI | DAG 재실행 시 결과 동일, 테스트 통과 | 없음 |
| 2. 스트리밍·매치데이 자동 분석 ✅ | Kafka, football-data.org 폴링 수집기, 과거 시즌 재생기, 수동 배당 이벤트, 마감 전 정해진 시각의 자동 스냅샷 | 이벤트 중복·지연 도착 처리, 분당 요청 제한 준수, 정해진 시각마다 스냅샷 누락 없음 | football-data.org 키 |
| 3. 모델·검증 ✅ | EPL Poisson/Dixon-Coles 기준 모델, 시간순 백테스트, 시장 배당 비교, 모의 기록 | 누수 검사 통과, Log loss·Brier를 기준 모델·배당과 비교, 보류율 공개 | 없음 |
| 4a. 레이크·Spark ✅ | Gold → Parquet(S3 lake 버킷, 시즌 파티션), Spark로 특징 재계산, dbt 결과와 행 단위 대조. 매일 DAG 끝에서 자동 실행(대조 실패 시 작업 실패) | 대조 불일치 0, CI에서 Spark 테스트 | 없음 |
| 4b. 텔레그램 알림 ✅ | 경기 전 스냅샷·주간 채점·작업 실패를 텔레그램으로 보냄(들어오는 길 없이 내보내기), 보낸 기록으로 중복 방지 | 같은 알림 한 번만, 토큰이 로그에 없음 | 봇 토큰·대화방 ID(.env) |
| 4c. 서빙·배포 | (필요하면) 조회 웹 화면, kind/k3d 배포 | 미니 PC에서 상시 운영 | 미니 PC 도입 |


## 3단계 세부 계획

| 단위 | 내용 | 상태 |
|---|---|---|
| 3a | 시간순 학습 데이터셋 `gold.match_features_pit`(과거 재구성 가정: 결과는 시작 3시간 뒤 공개), 두 겹의 누수 검사 | ✅ |
| 3b | 기준 모델: 단순 비율 → Poisson → Dixon-Coles, 주 단위 재학습 백테스트(검증 시즌에서 설정 선택, 시험 시즌은 한 번만 평가), 기록이 적은 팀은 리그 평균 쪽으로 축소, 실행·예측을 `modeling` 스키마에 버전과 함께 기록 | ✅ |
| 3c | 평가 보고서: 주 단위 블록 부트스트랩 불확실성, 확률 보정(ECE·Wilson 구간), 약한 곳(승격 팀·시즌 초반·무승부), 검증 기준(VALIDATED/NOT_VALIDATED), `modeling.evaluation_reports`와 자동 생성 Markdown | ✅ |
| 3d | 경기 전 스냅샷에 모델 예측 저장(같은 as_of를 DB가 강제, 검증 기준 통과 전에는 WITHHELD), 경기 후 채점, 주간 보고서 DAG(`weekly_model_report`, 화요일 06:00 UTC) | ✅ |
| 3e | 모델 개선: 승격 첫 시즌 효과, 확률 보정 계수, openfootball 2020-21 추가, 검증 두 시즌(2021-22·2022-23)으로 선택 안정화. 승격 팀 과대평가 해소, 전체 개선은 95% 구간이 0을 살짝 포함, 여전히 NOT_VALIDATED | ✅ |
| 3f | 교차 보정: 검증 두 시즌을 서로 바꿔 보정 계수를 채점해 선택 낙관(0.0009~0.0021)을 없앰. 활성 모델은 공정한 점수로도 Poisson+보정 | ✅ |

## 경기 주기에 맞춘 자동 분석 (준실시간)

경기는 매주 열리므로, 사람이 매번 실행하지 않아도 일정·결과·배당이 들어오는 대로 분석이 갱신되게 합니다. 목표는 초 단위 실시간이 아니라 **경기 주기에 맞춘 분 단위 자동 갱신**입니다.

| 시점 | 자동으로 하는 일 | 구현 |
|---|---|---|
| 매일 | 다음 경기 일정과 일정 변경 수집 | Airflow 일 단위 DAG(openfootball, football-data.org) |
| 입력이 바뀔 때 | 배당·일정·기록 변경 이벤트를 받아 스냅샷 추가 | Kafka 토픽(`fixtures`, `results`, `odds_manual`) 소비자 |
| 경기 당일 | 결과 폴링(대회별 일괄 조회, 분당 10회 한도 안에서 수 분 간격) | Kafka 생산자, 429 응답 시 대기 |
| 경기 종료 후 | 결과 버전 저장, 공식 결과 대조, 예측 평가 갱신 | 결과 이벤트 → 대조·평가 작업 |
| 매주 | 최근 성능 보고서(Log loss·Brier·보류율) 생성 | Airflow 주 단위 DAG (3단계: 모델이 생긴 뒤) |
| 새 예측·큰 변화 | 휴대폰 알림 | 텔레그램(4b): 경기 전 스냅샷, 주간 채점, 작업 실패 |


왜 중요한가: 마감 전에 실제로 저장한 스냅샷이 쌓여야 운영 성능(PROSPECTIVE)을 정직하게 평가할 수 있습니다. 과거 자료로 재구성한 백테스트만으로는 실제 수집 지연을 재현할 수 없습니다. 3단계 모델 전에는 같은 일정으로 입력·특징 스냅샷만 저장하며 확률은 만들지 않습니다.

한계
- 경기 중 실시간(인플레이) 예측은 범위 밖입니다. 경기 중 이벤트 데이터를 허용 조건으로 확보하지 못했습니다.
- 무료 API는 요청 한도와 갱신 지연이 있습니다. 라인업은 사용 조건을 확인한 소스가 생길 때까지 직접 입력합니다.
- 로컬 실행 구조라 PC가 켜져 있어야 자동 작업이 돕니다. 꺼져 있던 동안 놓친 작업은 다음 실행 때 보충하고, 놓친 마감 전 스냅샷은 사후에 만들지 않고 누락으로 기록합니다.

## 디렉터리 계획

```text
infra/                 # docker-compose, 이후 Helm 차트
pipelines/
  ingest/              # openfootball, football-data.co.uk, football-data.org
  streaming/           # Kafka 생산자·소비자(2단계)
  spark/               # Spark 작업(2~3단계)
dbt/                   # Gold 모델과 테스트
dags/                  # Airflow DAG
src/                   # 기존 도메인 로직(검증·규칙·시점)
```

## 결정 대기

- GitHub 공개 시점: 현재 정책은 main 미푸시 커밋 20개마다 푸시합니다.
- 모바일 외부 접속 방식(4단계): 개인 VPN 등. 127.0.0.1 원칙을 바꾸는 결정입니다.
- 자동 분석 상시 실행 환경(2단계): 이 PC를 켜 두고 쓸지, 항상 켜진 별도 장비를 둘지 결정이 필요합니다.
